# 2. Системный анализ и требования

## 2.1. Функциональные требования

Требования сгруппированы по подсистемам. Идентификатор формата `FR-<подсистема>-<номер>`.

### 2.1.1. Аутентификация и профиль (FR-A)

| ID | Требование | Приоритет |
|----|------------|-----------|
| FR-A-1 | Система должна поддерживать регистрацию пользователя по e-mail и паролю через Supabase Auth | MUST |
| FR-A-2 | Система должна автоматически создавать запись в `public.users` при регистрации (триггер `handle_new_user`) | MUST |
| FR-A-3 | Пользователь должен иметь возможность задать пол, возраст, рост, вес, уровень активности и цель | MUST |
| FR-A-4 | Система должна сохранять цели по калориям (`caloriesGoal`) и белку (`proteinGoal`) | MUST |
| FR-A-5 | Пользователь должен иметь возможность выйти из системы | MUST |

### 2.1.2. Учёт продуктов (FR-P)

| ID | Требование | Приоритет |
|----|------------|-----------|
| FR-P-1 | Пользователь должен иметь возможность добавить съеденный продукт вручную (имя, КБЖУ, вес, дата) | MUST |
| FR-P-2 | Пользователь должен иметь возможность редактировать и удалять записи | MUST |
| FR-P-3 | Система должна поддерживать поиск по справочнику `products` | SHOULD |
| FR-P-4 | Система должна группировать продукты по дате (день) | MUST |
| FR-P-5 | Удаление записи должно работать оптимистично (UI обновляется до подтверждения) | SHOULD |

### 2.1.3. Фото-анализ (FR-F)

| ID | Требование | Приоритет |
|----|------------|-----------|
| FR-F-1 | Пользователь должен иметь возможность загрузить фотографию блюда (камера или галерея) | MUST |
| FR-F-2 | Изображение должно сжиматься на клиенте перед отправкой (≤ 1 МБ) | SHOULD |
| FR-F-3 | Edge Function должна создавать запись со статусом `pending` и запускать фоновый анализ | MUST |
| FR-F-4 | LLM-провайдер должен возвращать структурированный JSON `{food_name, calories, protein, weight, confidence}` | MUST |
| FR-F-5 | Запись должна обновляться в Postgres со статусом `completed`/`error` | MUST |
| FR-F-6 | UI должен подписываться на Realtime-канал и показывать уведомление при завершении анализа | MUST |
| FR-F-7 | При `confidence == "low"` запись должна сохраняться, но помечаться визуально | SHOULD |
| FR-F-8 | Архитектура должна допускать замену LLM-провайдера без изменения вызывающего кода (Factory Method) | MUST |

### 2.1.4. Расчёт целей (FR-G)

| ID | Требование | Приоритет |
|----|------------|-----------|
| FR-G-1 | Система должна рассчитывать BMR по формуле Mifflin–St Jeor (по умолчанию) | MUST |
| FR-G-2 | Система должна поддерживать альтернативную формулу Harris–Benedict (выбор стратегии) | SHOULD |
| FR-G-3 | TDEE = BMR × коэффициент активности (5 уровней) | MUST |
| FR-G-4 | Calories Goal = TDEE + поправка (loss: −500, maintain: 0, gain: +400) | MUST |
| FR-G-5 | Protein Goal = вес × коэффициент активности (0.8…1.8 г/кг) | MUST |

### 2.1.5. Визуализация (FR-V)

| ID | Требование | Приоритет |
|----|------------|-----------|
| FR-V-1 | Главный экран должен показывать прогресс по калориям и белку за выбранный день | MUST |
| FR-V-2 | Должен быть график недельного потребления калорий | SHOULD |
| FR-V-3 | Кружки дней недели должны отображать % выполнения цели | SHOULD |
| FR-V-4 | На узких экранах (< 480 px) визуализация недели адаптируется | SHOULD |

## 2.3. Ограничения

| ID | Ограничение | Источник |
|----|-------------|----------|
| C-1 | Только PWA, нативные приложения не разрабатываются | Курсовая работа |
| C-2 | Бэкенд — только Supabase (Postgres / Auth / Storage / Edge Functions) | Архитектурное решение |
| C-3 | LLM-провайдер — OpenRouter (бесплатные квоты Gemini) | Бизнес-ограничение бюджета |
| C-4 | Квота OpenRouter ограничена (≈ 50 запросов/мин для free-tier) | Внешнее ограничение |
| C-5 | Edge Function исполняется на Deno; нельзя использовать Node-only пакеты | Платформа |
| C-6 | Размер изображения после сжатия ≤ 4 МБ (лимит OpenRouter / Storage) | Внешнее ограничение |
| C-7 | Хранение данных в одном регионе (eu-central-1) | Конфигурация Supabase |

## 2.4. Допущения

- Пользователь имеет аккаунт Google или e-mail и доступ к интернету для первого запуска.
- Камера устройства обеспечивает разрешение ≥ 1024 × 768.
- Часовой пояс пользователя совпадает с системным временем устройства.

## 2.5. Сценарии использования (Use Cases)

### UC-1. Добавление продукта по фото

1. Пользователь нажимает кнопку «+» и выбирает «Сделать фото».
2. Браузер запрашивает доступ к камере; пользователь делает снимок.
3. Клиент сжимает изображение и отправляет в `POST /functions/v1/analyze-food-photo` (multipart).
4. Edge Function загружает фото в Storage, создаёт запись со статусом `pending`, отвечает 202 + `id`.
5. UI оптимистично добавляет карточку со скелетоном.
6. Edge Function в фоне вызывает LLM, парсит ответ, обновляет запись (`completed` или `error`).
7. Realtime-канал доставляет UPDATE-событие, UI обновляет карточку и показывает уведомление.

### UC-2. Изменение цели по калориям

1. Пользователь открывает «Профиль» → «Калькулятор калорий».
2. Заполняет анкету (пол, возраст, рост, вес, активность, цель).
3. Клиент через `calculateGoals(params, strategy)` рассчитывает BMR/TDEE/Calories/Protein.
4. По кнопке «Сохранить» цели записываются в `public.users`.

### UC-3. Просмотр прогресса за неделю

1. Главный экран загружает `useGetWeeklyFoodsQuery`.
2. Хук вычисляет `monday = getMondayOfWeek(today)` и делает запрос за 7 дней.
3. На экране отображаются кружки прогресса и график калорий.
